# Zoho draft push — design

Status: approved by owner (Approach A), 2026-08-24. Not yet implemented.

## Problem

`/outreach` already drafts personalised first-touch emails per business and
writes them to `~/wardith-runs/<slug>/outreach/outreach-prep-<slug>-<date>.{json,md}`
for manual review. The owner then hand-copies each one into Zoho Mail
(`mail.zoho.eu` or `mail.zoho.com` — which data center is confirmed during
setup, see Open questions) to actually send it. The owner wants that copy
step gone: after a `/outreach` run, every
drafted email should already be sitting in the Zoho Drafts folder, ready to
open, edit if needed, and send.

## Non-goals

- **Never sends, replies, or deletes anything.** The only capability added is
  creating/updating a draft. This is the one constraint everything else in
  this design is built to protect, including against a future edit to this
  code — see "Auditability" below.
- Does not touch LinkedIn drafts — those stay exactly as `/outreach` produces
  them today (text only, no API, per `playbook/decisions.md`'s "LinkedIn
  outreach is later, not now").
- Does not change `/outreach`'s Stages 1–7 (who gets drafted, what the email
  says, the contact-route re-check). Only adds a step after Stage 7.
- Does not manage the Zoho account itself (no signature sync, no folder
  management) — the signature is Zoho's own "new mail" setting, per
  `assets/brand/email-signature.html`'s own instructions; this script never
  touches it.

## Why a script, not an MCP server

Investigated during brainstorming:

- **Zoho's official MCP server** exists (`zoho.com/mail/help/mcp/`, lists
  Claude as a supported client) but does not appear under the owner's own
  Zoho Mail → Developer Space settings — not available on this account/plan.
  REST API access **is** available there (confirmed by screenshot), which is
  what this design uses directly.
- **A generic third-party Zoho Mail MCP server** (e.g. the one on GitHub)
  would work but exposes send/reply/delete tools alongside create-draft —
  more capability sitting next to this workflow than it needs, in
  unreviewed code, touching a real mailbox. Rejected on the same reasoning
  CLAUDE.md/AGENTS.md already applies elsewhere in this repo: don't grant a
  capability nothing here needs.
- **A purpose-built script**, called deterministically at the end of
  `/outreach`, matches this repo's existing convention exactly —
  `scoring_engine.py`'s own docstring: "Deterministic computation only."
  Pushing already-fixed text to a fixed endpoint is mechanical, not a
  judgement call, so it belongs in `tools/`, not routed through an LLM tool
  call.

## Architecture

```
tools/zoho-draft-push/
  zoho_draft_push.py       the script /outreach's Stage 7.5 runs
  setup_zoho_oauth.py       one-time credential setup, run manually by the owner
  test_zoho_draft_push.py   unit tests (HTTP layer mocked, no real credentials)
  README.md                 setup walkthrough + usage
```

```
Owner (one-time, manual, in their own browser)
  → api-console.zoho.com: register a Self Client, scopes
    ZohoMail.messages.CREATE + ZohoMail.accounts.READ, generate a grant token
  → `python3 tools/zoho-draft-push/setup_zoho_oauth.py --client-id ... \
       --client-secret ... --grant-token ... --region eu`
  → exchanges grant token for a refresh token, looks up account_id,
    writes ~/.wardith/zoho-credentials.json (outside the repo)

/outreach, Stage 7.5 (new), every run
  → `python3 tools/zoho-draft-push/zoho_draft_push.py \
       --input <outreach-prep-slug-date>.json --in-place`
  → refreshes an access token from the stored refresh token
  → for each entry where withheld=false:
      has zoho_draft_id already? → PUT (update existing draft)
      else                       → POST (create new draft), store the
                                    returned id back into the entry
  → writes per-entry zoho_push_status/zoho_pushed_at back into the JSON
  → prints a summary: pushed / updated / failed / skipped
```

## Credential handling

- Generated by the owner directly in Zoho's own API console — Claude never
  sees a Zoho password, and never types anything into a Zoho login page.
- Stored at `~/.wardith/zoho-credentials.json` (path overridable via
  `WARDITH_ZOHO_CREDENTIALS` env var), **outside this repository**, matching
  the existing "client data lives outside the repo, encrypted, on the
  owner's own machine" pattern (`playbook/records-and-data.md`,
  `playbook/accounts-and-dates.md`).
- Contains: `client_id`, `client_secret`, `refresh_token`, `account_id`,
  `api_domain` (e.g. `https://mail.zoho.eu`), `accounts_domain` (e.g.
  `https://accounts.zoho.eu`). Region is asked at setup time, not assumed —
  Zoho provisions accounts to different regional data centers and the wrong
  one fails every call outright, so this is a setup-script question, not a
  guess baked into the code.
- `.gitignore` gets a defensive entry (`zoho-credentials.json`,
  `.wardith/`) even though the real credentials never live inside the repo
  — the same belt-and-braces reasoning already applied to
  `.claude/settings.local.json`.
- Nothing in `tools/zoho-draft-push/` ever logs the client secret or full
  refresh/access token — setup script echoes only a masked confirmation.

## Auditability — the "can this ever send" property

This is the property the design most needs to hold, so it's stated
explicitly rather than left implicit in the code:

`zoho_draft_push.py` makes exactly three kinds of HTTP call, all to
fixed, hard-coded paths:

1. `POST {accounts_domain}/oauth/v2/token` — refresh the access token.
2. `GET {api_domain}/api/accounts` — look up the account id (setup only).
3. `POST` / `PUT {api_domain}/api/accounts/{account_id}/messages` with
   `mode: "draft"` — create or update a draft.

No other Zoho endpoint is referenced anywhere in the file — no reply, no
delete, no folder move. Those are separate Zoho API surfaces needing scopes
this token doesn't carry, and the code never calls them.

**Correction, 2026-08-25** (this spec originally claimed the OAuth scope
made a send impossible; that was wrong, and the error is recorded here
rather than quietly overwritten, since this spec is the authority the
implementation plan argued from). Zoho's "Send an Email" and "Save Draft or
Template" APIs are the *same* endpoint (`POST .../messages`), the same
HTTP method, and the same scope — `ZohoMail.messages.CREATE` is documented
as valid for both. The only thing distinguishing a send from a draft-save is
the request body's `mode` field, so the scope alone rules out nothing here.

**Second correction, same date** (found by the re-review of the fix for the
first one — the same error class survived one sentence away, because the
"no reply, no delete, no folder move" line just above was assumed correct
rather than re-checked). "Those are separate Zoho API surfaces needing
scopes this token doesn't carry" is also wrong for Reply specifically:
Zoho's Reply API is documented under this same `ZohoMail.messages.CREATE`
scope. Delete and folder-move genuinely do need scopes this token lacks.
The accurate claim for all three is narrower: this code never calls any of
them, not that the scope prevents it.

The real property, which is still sufficient, is how the payload is built:
`build_message_payload()` returns a closed dict of six literal keys
(`fromAddress`, `toAddress`, `subject`, `content`, `mailFormat`, `mode`)
with `mode` hardcoded to `"draft"` unconditionally. Entry data is read only
into named values; no entry dict is ever merged into the payload, so no
business's outreach content can reach or override `mode`. This is called out
as an invariant in the file's own docstring (mirroring how
`scoring_engine.py` states its own invariants up top) *and* enforced by
`DraftModeInvariantTests` in `test_zoho_draft_push.py`, so a future edit has
to consciously violate a stated rule and delete passing tests to add a send
path, not just add a line.

## Data shape changes

`outreach-prep-<slug>-<date>.json` (defined in `/outreach`'s Stage 7) gains
three optional fields per business entry, written by `zoho_draft_push.py`,
never by `/outreach` itself:

```
"zoho_draft_id": "... or null",       // Zoho's message id, for update-in-place on rerun
"zoho_push_status": "OK" | "FAILED: <reason>" | "SKIPPED (withheld)",
"zoho_pushed_at": "YYYY-MM-DDThh:mm:ssZ or null"
```

Re-running `/outreach` on the same campaign (a correction, a re-verified
contact route) reuses the stored `zoho_draft_id` and updates the existing
Zoho draft in place rather than creating a duplicate.

## Error handling

- **A single business's push failing (network blip, stale token mid-run,
  Zoho-side validation) never stops the batch.** Recorded as
  `zoho_push_status: "FAILED: <reason>"`, script moves to the next entry —
  same "collect every problem, don't halt on the first one" pattern
  `build_workbook.py --require-scored` already uses.
- **A structural failure (refresh token rejected, no credentials file at
  all) stops the whole run before any business is processed**, with a clear
  message pointing at `tools/zoho-draft-push/README.md`'s setup steps — this
  is the one case worth failing loud and early, since every subsequent call
  would fail identically.
- `--dry-run` flag: builds and logs what would be sent for each business
  without making the create/update call. Useful for testing the mapping
  without touching the real mailbox.

## `/outreach` skill changes

Applies to both `.claude/skills/outreach/SKILL.md` and
`.agents/skills/outreach/SKILL.md`:

- **Stage 0's scope statement** is revised from an unqualified "No sends. No
  email client... nothing that posts, submits, or transmits outreach
  anywhere" to something precise: creating/updating a Zoho **draft** via a
  token that can only create drafts is not a send, and is now part of what
  this skill does; sending, replying, and deleting remain absolutely out of
  scope, same as today.
- **New Stage 7.5 — Push drafts to Zoho Mail**, immediately after Stage 7
  writes the local files: run `zoho_draft_push.py --input <the file just
  written> --in-place`.
- **Stage 8's report** gains a line: how many drafts pushed/updated in Zoho,
  how many failed and why, and a reminder that they're sitting in Zoho
  Drafts for review before anyone clicks send.
- **"What this skill does not do"** tightened to state the one Zoho
  capability precisely instead of an absolute "does not call any sending
  API" that would now be inaccurate.

## Testing

`test_zoho_draft_push.py`, mocking `urllib.request.urlopen` (matching
`trade_run.py`'s own stdlib-only HTTP pattern — no new pip dependency):

- New entry (no `zoho_draft_id`) → POST called, returned id recorded.
- Entry with existing `zoho_draft_id` → PUT called, not POST.
- `withheld: true` entry → skipped, no HTTP call, status recorded as such.
- One entry's call raising an HTTP error → recorded as FAILED, remaining
  entries still processed.
- Token refresh failure → script exits non-zero before any per-entry call,
  clear message.
- `--dry-run` → no HTTP calls to the messages endpoint at all.
- Summary counts (pushed/updated/failed/skipped) match the fixture.

## Open questions for the owner (resolve during setup, not design)

1. **Which Zoho data center/region** — `.eu` or `.com`? Needed for
   `api_domain`/`accounts_domain`. Determined when the owner registers the
   Self Client (the API console URL itself indicates the region), recorded
   by `setup_zoho_oauth.py`, not assumed here. **Resolved 2026-08-26: `.eu`.**
   One real-setup wrinkle worth recording: generating the grant token's two
   required scopes (`ZohoMail.messages.CREATE`, `ZohoMail.accounts.READ`)
   separately in Zoho's console produces two single-scope, single-use
   tokens, neither of which alone authorizes both calls this tool makes.
   Both scopes must be entered together in one generation step to get one
   combined token — confirmed by hitting `INVALID_OAUTHSCOPE` on the
   account-lookup call after exchanging a `.create`-only token first.
2. **Does Zoho auto-apply the account's "new mail" signature to a draft
   created via the API**, or only to ones composed through the web UI?
   **Resolved 2026-08-26, on the first real test draft: no, it does not.**
   The owner adds the signature manually per draft before sending — this
   was always the fallback this spec anticipated (see Non-goals: not solved
   by having the script duplicate the signature HTML), now confirmed as the
   actual, permanent behavior rather than a possibility to watch for.
3. **The Zoho account this tool authenticates against uses a send-as alias**
   — the underlying mailbox is `hello@novenstudio.co.uk`, but the owner has
   configured `hello@wardith.co.uk` as an alias and wants drafts to send
   from that address. Zoho's account-lookup response doesn't reliably
   surface which alias to prefer (this spec's design only ever read
   `primaryEmailAddress`), so `setup_zoho_oauth.py` recorded the wrong
   address on first run and `from_address` was corrected by hand in
   `~/.wardith/zoho-credentials.json` after setup. Not a design gap worth
   solving in code for a one-mailbox, one-operator setup — YAGNI — but
   worth knowing if setup is ever re-run: check `from_address` in the
   written credentials file against what the owner actually wants before
   trusting it.
